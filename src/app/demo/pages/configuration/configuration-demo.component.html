Les composants ci-dessous ne changent pas : seuls leurs défauts changent. Le code à droite est ce que vous écririez une fois, au bootstrap.

L'appel

import { bootstrapApplication } from '@angular/platform-browser';
import { provideHelix } from 'ps-helix';

bootstrapApplication(AppComponent, {
  providers: [
    provideHelix({
      theme: { targetContrast: 'AAA', customerContext: BrandService },
      components: {
        button: { size: 'large', appearance: 'outline' },
        modal: { dismissLabel: 'Fermer', confirmLabel: 'Valider' },
        toast: { position: 'bottom-right' },
      },
    }),
  ],
});

Une surcharge partielle reste partielle. Chaque composant lit this.config.<clé> ?? <son propre littéral>, donc régler la taille d'un bouton ne remet pas sa couleur ni son apparence à zéro.

Un attribut l'emporte toujours. La configuration fixe le défaut de l'input ; l'écrire sur un élément le surcharge pour cet élément.

Plus fin

Trois fonctions couvrent une partie chacune, et se mélangent sans dommage :

provideHelixTheme({ targetContrast: 'AAA' })
provideHelixComponentDefaults({ button: { size: 'large' } })
provideHelixToast({ position: 'bottom-right', duration: 3000 })

Et chaque token est exporté nommément, pour le cas où un coin de l'application a besoin d'un défaut différent : 

import { BUTTON_CONFIG } from 'ps-helix';

@Component({ providers: [{ provide: BUTTON_CONFIG, useValue: { size: 'small' } }] })
export class ToolbarComponent {}

Une valeur peut être une fonction

Une chaîne est lue une fois, à la construction du composant — ce qu'il faut pour une langue fixée au démarrage. Une fonction est relue à chaque besoin, donc un sélecteur de langue met à jour les composants déjà affichés. 

provideHelix({
  components: {
    select: { placeholder: () => t.instant('psh.select.placeholder') },
  },
})

Réservé à la prose : size, appearance, placement et leurs semblables restent des valeurs simples — on ne les traduit pas.

Ce qu'on peut régler

31 tokens, 226 défauts, dont 49 traduisibles. La liste exhaustive est dans CONFIGURATION.md, générée depuis les tokens eux-mêmes : une valeur par défaut qui bouge dans le code bouge dans la documentation au prochain npm run docs:config, et l'intégration continue échoue si les deux divergent.

Pourquoi ce n'est pas une déclaration CSS

Les défauts visuels passent par les custom properties, pas par cette configuration — et elles sont lues en var(--psh-x, défaut) plutôt que déclarées sur :host. Une déclaration sur :host compile en [_nghost-…], soit une spécificité de (0,1,0), qui bat une règle psh-button { … } écrite dans la feuille de style d'une application. Le défaut gagnait donc contre la surcharge. Un var() de repli n'a aucune spécificité à opposer.

Le garde-fou

TOKEN_BY_KEY est vérifié par satisfies Record<keyof Required<PshComponentDefaults>, unknown> : un composant ajouté à l'interface sans token — ou l'inverse — est une erreur de compilation, pas une clé qu'on peut écrire et que rien ne lit. Et une suite de tests passe la configuration de chaque composant à travers un Proxy qui enregistre les lectures : un défaut déclaré que personne ne lit fait échouer la CI. Quatre tokens étaient dans ce cas avant qu'elle existe.

Bonnes Pratiques

  • Un seul appel à provideHelix() au bootstrap, plutôt qu'un attribut répété sur chaque élément.
  • Ne configurez que ce qui diffère : le reste reste au défaut de la bibliothèque, et suivra ses évolutions.
  • Pour la langue, partez de PSH_FRENCH_DEFAULTS et fusionnez vos écarts — voir la page Internationalisation.
  • Un token par composant (BUTTON_CONFIG…) pour un coin d'application, pas pour l'application entière.
